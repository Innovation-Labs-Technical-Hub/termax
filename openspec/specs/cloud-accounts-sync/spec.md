# cloud-accounts-sync Specification

## Purpose

Define requirements for the closed `oxsync` service (Pro and above): zero-knowledge accounts (OPAQUE login, 2SKD Secret Key, trusted devices, MFA, SSO for Business) and local-first E2EE sync of hosts, identities, keys, snippets, known hosts and settings across desktop and mobile. The server stores only ciphertext and minimal metadata; losing the server never loses data because every device keeps a full copy.

Source: BRD-10 “Cloud: accounts & E2EE sync” v1.0 (draft) (2026-10-30). Modules: CL-01, CL-02. Generated by `tools/openspec_from_brd.py`; edit through OpenSpec changes.

## Requirements

### Requirement: FR-CL01-001 Account sign-up with OPAQUE
The system SHALL provide: Account sign-up with OPAQUE.

Source: BRD-10 FR-CL01-001 · Module: CL-01 · Priority: Must · Phase: P2  
VI: Đăng ký tài khoản bằng OPAQUE

#### Scenario: FR-CL01-001 specified behaviour
- **GIVEN** the system implements FR-CL01-001
- **THEN** The client runs OPAQUE registration (`opaque-ke`, Ristretto255, Argon2id as the KSF) so the server stores only the registration record; the password never leaves the device. The email is verified with a one-time link before sync is activated

#### Scenario: FR-CL01-001 acceptance 1
- **GIVEN** a proxy recording all sign-up traffic
- **WHEN** searching for the password and any Argon2id hash of it
- **THEN** there are no matches

#### Scenario: FR-CL01-001 acceptance 2
- **GIVEN** an unverified email
- **WHEN** the client calls the record push API
- **THEN** the server returns 403 email_unverified

### Requirement: FR-CL01-002 2SKD Secret Key and Emergency Kit
The system SHALL provide: 2SKD Secret Key and Emergency Kit.

Source: BRD-10 FR-CL01-002 · Module: CL-01 · Priority: Must · Phase: P2  
VI: 2SKD Secret Key và Emergency Kit

#### Scenario: FR-CL01-002 specified behaviour
- **GIVEN** the system implements FR-CL01-002
- **THEN** At sign-up the device generates a 128-bit Secret Key from the OS RNG (versioned format with checksum, e.g. A3-XXXXXX-...). Account Unlock Key = HKDF(OPAQUE export key, Secret Key). The Emergency Kit (PDF with QR, email, sign-in URL and a blank for the password) is generated locally and never uploaded

#### Scenario: FR-CL01-002 acceptance 1
- **GIVEN** a full server database dump and the correct password
- **WHEN** trying to decrypt the account private key without the Secret Key
- **THEN** decryption fails

#### Scenario: FR-CL01-002 acceptance 2
- **GIVEN** the user clicks 'I saved my Emergency Kit' without downloading or printing it
- **WHEN** continuing
- **THEN** the app asks them to re-type the last 4 characters of the Secret Key

### Requirement: FR-CL01-004 Trusted devices, sessions and revocation
The system SHALL provide: Trusted devices, sessions and revocation.

Source: BRD-10 FR-CL01-004 · Module: CL-01 · Priority: Must · Phase: P2  
VI: Thiết bị tin cậy, phiên đăng nhập và thu hồi

#### Scenario: FR-CL01-004 specified behaviour
- **GIVEN** the system implements FR-CL01-004
- **THEN** Each device has a device key pair (X25519 for sealing, Ed25519 for signing) kept in the OS keychain/Secure Enclave/Keystore. The device list shows name, platform, app version, last-seen and truncated IP; the user can revoke one device or 'Sign out everywhere'. #### Scenario: FR-CL01-004 acceptance 1
- **GIVEN** device B is revoked from device A
- **WHEN** B calls any sync API
- **THEN** the server returns 401 device_revoked within ≤5 s of revocation and B wipes its cached cloud keys on receipt

#### Scenario: FR-CL01-004 acceptance 2
- **GIVEN** a refresh token copied to another machine
- **WHEN** it is used without a device-key signature
- **THEN** the server rejects it and records a security event

### Requirement: FR-CL01-005 New-device approval from a trusted device

Source: BRD-10 FR-CL01-005 · Module: CL-01 · Priority: Should · Phase: P2

### Requirement: FR-CL01-008 Recovery for individual accounts

Source: BRD-10 FR-CL01-008 · Module: CL-01 · Priority: Must · Phase: P2

#### Scenario: FR-CL01-008 acceptance 1

#### Scenario: FR-CL01-008 acceptance 2
- **GIVEN** a user has no password, Secret Key, recovery code or trusted device
- **WHEN** contacting support
- **THEN** the support runbook only allows deleting and re-creating the account, never data recovery

### Requirement: FR-CL01-010 Organisation recovery (admin escrow, opt-in)
The system SHALL provide: Organisation recovery (admin escrow, opt-in).

Source: BRD-10 FR-CL01-010 · Module: CL-01 · Priority: Should · Phase: P3  
VI: Organisation recovery (admin escrow, opt-in)

#### Scenario: FR-CL01-010 specified behaviour
- **GIVEN** the system implements FR-CL01-010
- **THEN** Business orgs can enable organisation recovery: the member's org membership key (which unseals team vault keys) is additionally sealed to the org recovery public key, whose private key is sealed to each admin. #### Scenario: FR-CL01-010 acceptance 2
- **GIVEN** a member with their own password (not an SSO-managed account) and a personal vault
- **WHEN** an admin uses recovery
- **THEN** the admin restores team-vault access only and cannot decrypt that personal vault

### Requirement: FR-CL01-011 Account deletion
The system SHALL provide: Account deletion.

Source: BRD-10 FR-CL01-011 · Module: CL-01 · Priority: Must · Phase: P2  
VI: Xoá tài khoản

#### Scenario: FR-CL01-011 specified behaviour
- **GIVEN** the system implements FR-CL01-011
- **THEN** Users delete their account in-app (MFA required). There is a 7-day cancellable waiting period; afterwards ciphertext, blobs, snapshots, devices and metadata are hard-deleted from the primary DB within ≤72 h and age out of backups within ≤35 days. Invoices are retained for accounting obligations. Local data is untouched

#### Scenario: FR-CL01-011 acceptance 1

- **WHEN** the deletion job runs
- **THEN** queries by account_id across all tables and buckets return 0 rows within ≤72 h and the job records a content-free deletion receipt

### Requirement: FR-CL02-001 Per-record encryption and record envelope
The system SHALL provide: Per-record encryption and record envelope.

Source: BRD-10 FR-CL02-001 · Module: CL-02 · Priority: Must · Phase: P2  
VI: Mã hoá per-record và envelope record

#### Scenario: FR-CL02-001 specified behaviour
- **GIVEN** the system implements FR-CL02-001
- **THEN** Each record (host, identity, key, snippet, known host, settings group) is encrypted with XChaCha20-Poly1305 under the vault key, a random 192-bit nonce, and AAD = vault_id ‖ record_id ‖ key_id ‖ schema_version. Record kind and all fields are inside the ciphertext; the server sees only vault_id, a random record_id (UUIDv4), padded size and seq

#### Scenario: FR-CL02-001 acceptance 1
- **GIVEN** the server moves record A's ciphertext under record_id B
- **WHEN** the client decrypts
- **THEN** AAD authentication fails, the record is rejected and an integrity event is logged

#### Scenario: FR-CL02-001 acceptance 2
- **GIVEN** two records of the same kind with 300 B and 900 B content
- **WHEN** observed on the server
- **THEN** both have the same ciphertext size (1 KiB bucket)

### Requirement: FR-CL02-002 Push/pull protocol with per-vault sequence
The system SHALL provide: Push/pull protocol with per-vault sequence.

Source: BRD-10 FR-CL02-002 · Module: CL-02 · Priority: Must · Phase: P2  
VI: Giao thức push/pull theo seq của vault

#### Scenario: FR-CL02-002 specified behaviour
- **GIVEN** the system implements FR-CL02-002
- **THEN** Clients push batches of ops (≤500 ops or ≤1 MiB) with client-generated op_ids for idempotency; the server assigns a monotonically increasing per-vault seq and returns it. Pull uses a paginated 'since seq' cursor. The server never merges (it cannot read content); all merging happens on clients

#### Scenario: FR-CL02-002 acceptance 1
- **GIVEN** the same batch is resent 3 times after network loss
- **WHEN** pulling from another device
- **THEN** each op appears exactly once

#### Scenario: FR-CL02-002 acceptance 2
- **GIVEN** cursor seq=1000 and 2,500 new ops
- **WHEN** pulling
- **THEN** the client receives all 2,500 ops across pages in seq order

### Requirement: FR-CL02-003 LWW with Lamport clocks
The system SHALL provide: LWW with Lamport clocks.

Source: BRD-10 FR-CL02-003 · Module: CL-02 · Priority: Must · Phase: P2  
VI: LWW với Lamport clock

#### Scenario: FR-CL02-003 specified behaviour
- **GIVEN** the system implements FR-CL02-003
- **THEN** Each record carries a Lamport clock (lamport, device_id) inside the ciphertext; when two versions touch the same field, the larger (lamport, device_id) wins. Wall-clock time is never used for ordering, so device clock skew has no effect

#### Scenario: FR-CL02-003 acceptance 1
- **GIVEN** device A's system clock is set 2 days back
- **WHEN** A edits a record after having seen B's version
- **THEN** A's version still wins because A's Lamport value is higher

Source: BRD-10 FR-CL02-004 · Module: CL-02 · Priority: Must · Phase: P2

#### Scenario: FR-CL02-004 specified behaviour
- **GIVEN** the system implements FR-CL02-004
- **THEN** Each record has a per-device vector clock (inside the ciphertext). For concurrent versions: auto-merge per field when fields differ; when the same field changed, LWW decides and the losing version is stored as a conflict copy linked to the original and surfaced in the conflict view (UI-11)

#### Scenario: FR-CL02-004 acceptance 1
- **GIVEN** A changes the port and B changes the user of the same host while offline
- **WHEN** both sync

- **GIVEN** A and B both change a host's address
- **WHEN** syncing
- **THEN** one version wins by LWW, the other becomes a conflict copy and a 'Conflicts (1)' badge appears on every device

### Requirement: FR-CL02-005 Tombstones and delete propagation
The system SHALL provide: Tombstones and delete propagation.

Source: BRD-10 FR-CL02-005 · Module: CL-02 · Priority: Must · Phase: P2  
VI: Tombstone và lan truyền xoá

#### Scenario: FR-CL02-005 specified behaviour
- **GIVEN** the system implements FR-CL02-005
- **THEN** Deletes create tombstones (empty payload, deleted flag) so offline devices also learn about them. Tombstones are compacted once every active device has acknowledged their seq, or after 90 days; a device offline for >90 days must re-bootstrap from a snapshot. In-app deletes have a 10 s undo before being pushed

#### Scenario: FR-CL02-005 acceptance 1
- **GIVEN** the phone is offline for 30 days while the desktop deletes 5 hosts
- **WHEN** the phone comes online
- **THEN** exactly those 5 hosts disappear on the phone

#### Scenario: FR-CL02-005 acceptance 2
- **GIVEN** a device offline for 120 days
- **WHEN** it reconnects
- **THEN** it is told to re-bootstrap from a snapshot and its unpushed local changes are preserved and pushed after bootstrap

### Requirement: FR-CL02-006 WebSocket fan-out
The system SHALL provide: WebSocket fan-out.

Source: BRD-10 FR-CL02-006 · Module: CL-02 · Priority: Must · Phase: P2  
VI: WebSocket fan-out

#### Scenario: FR-CL02-006 specified behaviour
- **GIVEN** the system implements FR-CL02-006
- **THEN** Clients hold one WebSocket (axum + tokio-tungstenite) subscribed to their vaults; on a new seq the server sends (vault_id, seq), inlining the ciphertext when the op is ≤16 KiB. On disconnect the client reconnects with jittered backoff (1 s → 60 s) and pulls the gap; where WebSockets are blocked it falls back to HTTP long-polling

#### Scenario: FR-CL02-006 acceptance 1
- **GIVEN** two online devices in the same region
- **WHEN** device A saves a host
- **THEN** device B shows the change with p95 ≤1 s (NFR-10-001)

#### Scenario: FR-CL02-006 acceptance 2
- **GIVEN** a corporate proxy blocks WebSockets
- **WHEN** the client connects
- **THEN** it switches to long-polling within ≤10 s and sync status remains 'Synced'

### Requirement: FR-CL02-007 Blob store for large items
The system SHALL provide: Blob store for large items.

Source: BRD-10 FR-CL02-007 · Module: CL-02 · Priority: Should · Phase: P2  
VI: Blob store cho item lớn

#### Scenario: FR-CL02-007 specified behaviour
- **GIVEN** the system implements FR-CL02-007

- **THEN** the client falls back to the older snapshot or full log replay and reports an integrity event

## Business rules

- **BR-10-01**: Local-first: the Free (Apache-2.0) app never requires an account; sync is an opt-in Pro-and-above feature.
- **BR-10-02**: The server never receives the password, Secret Key, Account Unlock Key, account private key, vault keys or record plaintext.
- **BR-10-03**: Individual accounts have no server-side recovery: losing the password, Secret Key, recovery code and every trusted device makes cloud data unrecoverable; this must be shown and acknowledged before sign-up completes.
- **BR-10-04**: A new device obtains keys only through one of three paths: password + Secret Key; approval from a trusted device; or (Business) admin approval via organisation recovery.
- **BR-10-05**: MFA guards access to ciphertext and account changes; it does not take part in key derivation.
- **BR-10-06**: Conflicts never silently drop data: the losing version is kept as a conflict copy until the user resolves it.
- **BR-10-07**: Entitlement lapse: after the grace period sync becomes read-only; local data always stays usable and exportable.
- **BR-10-08**: Deleting an account removes all cloud ciphertext; local data on devices stays unless the user chooses to wipe it.
- **BR-10-09**: Server logs, metrics and traces never contain ciphertext, record content, host names, commands, or full IP addresses beyond 30 days.
- **BR-10-10**: Sync opens to users in Vietnam/EU only after legal signs off the impact assessment and cross-border transfer dossier.

## User journeys

### J-10-01 Upgrade to Pro and enable sync on desktop
1. The user opens Team & Sync → Turn on sync, enters email and password.
2. The app runs OPAQUE registration, generates a 128-bit Secret Key on the device, shows the Emergency Kit (PDF + QR) and asks the user to confirm it is saved.
3. The app creates the account key pair, wraps it with the Account Unlock Key (OPAQUE export key + Secret Key via HKDF) and uploads the wrapped copy.
4. The local vault is encrypted per record with the vault key and pushed in batches; the status bar shows 'Synced · 0 pending'.

### J-10-02 Add a phone as a second device
1. On the phone, the user chooses Sign in and enters email + password.
2. They pick 'Approve from another device': the desktop receives the request and both screens show the same 6-digit verification code.
3. The user compares the codes and taps Approve on the desktop; the desktop seals the account key to the phone's public key.
4. The phone unlocks, downloads the latest snapshot plus the log tail and is ready offline; Face ID is offered for future unlocks.

### J-10-03 Concurrent offline edits and conflict resolution
1. A laptop (offline on a flight) changes host 'db-prod' port to 2222; the phone changes the same host's user to 'deploy'.
2. When the laptop is back online the outbox pushes; vector clocks show the two versions are concurrent.
3. Different fields merge automatically (port 2222 + user deploy); if the same field changed, the LWW version wins and the other is kept as a conflict copy.
4. A '1 conflict' banner opens the compare view (UI-11) to choose Keep mine / Keep theirs / Keep both.

### J-10-04 Business employee signs in with SSO on a new laptop
1. The employee chooses 'Sign in with SSO' and enters the work email; the app hands off to the IdP (Okta/Entra/Google) in the system browser.
2. After the IdP authenticates, the app creates a device key and sends a device-approval request.
3. The employee's existing trusted device, or an admin (if organisation recovery is on), approves; the account key is sealed to the new device key.
4. There is no separate encryption-password step; the vault unlocks and syncs.

## Data entities

- **accounts**: id, email, email_verified_at, opaque_registration, kdf_params, secret_key_version, x25519_pub, ed25519_pub, wrapped_private_keys, recovery_wrapped_key, region, status, delete_requested_at, created_at — wrapped_private_keys are wrapped by the AUK; the server cannot open them.
- **devices**: id, account_id, name_enc, platform, app_version, x25519_pub, ed25519_pub, sealed_account_key, approved_by, last_seen_at, last_ack_seq, revoked_at, push_token_enc — name_enc is encrypted under the account key so the server never sees device names.
- **auth_sessions**: id, device_id, refresh_token_hash, mfa_level, created_at, expires_at, ip_trunc — Refresh tokens bound to the device key (Ed25519 signature on refresh).
- **mfa_factors**: id, account_id, kind(totp|webauthn|backup), secret_sealed, credential_id, public_key, sign_count, last_used_step, created_at — TOTP secret encrypted with a server-side KMS key (authentication data, not vault keys).
- **sso_connections**: org_id, protocol(oidc|saml), issuer, client_id, metadata, verified_domains, enforce, recovery_enabled, created_at — Business, P3.
- **vault_records**: vault_id, record_id, seq, key_id, ciphertext, nonce, padded_size, deleted, op_id, pushed_by_device, created_at — Lamport, vector clock and record kind live inside the ciphertext.
- **blobs**: sha256, vault_id, size, key_id, storage_key, ref_count, created_at, orphaned_at — Stored on R2/S3; transferred via presigned URLs.
- **snapshots**: vault_id, snapshot_id, up_to_seq, blob_sha256, created_by_device, created_at — Two most recent kept.
- **sync_outbox (client)**: op_id, vault_id, record_id, ciphertext, attempts, last_error, created_at — Local SQLite, same transaction as the change.
- **security_events**: id, account_id, kind, device_id, ip_trunc, user_agent, created_at — Sign-ins, password changes, device approvals/revocations, recovery use; kept 1 year.

## Interfaces

- **IF-10-01 POST /v1/auth/opaque/{register,login}/{start,finish}** (HTTPS JSON (oxsync)): Two-round OPAQUE for registration and login; returns a session token once MFA is satisfied.
- **IF-10-02 /v1/devices (list, approve, revoke) + WS event device.approval_requested** (HTTPS JSON + WebSocket): Device management and new-device approval channel (sealed account key is delivered here).
- **IF-10-03 POST /v1/vaults/{id}/ops, GET /v1/vaults/{id}/ops?since={seq}** (HTTPS JSON/CBOR): Idempotent batch push and paginated cursor pull.
- **IF-10-04 GET /v1/stream (WebSocket)** (WebSocket (tokio-tungstenite)): Subscribe to vaults; receive (vault_id, seq[, ciphertext ≤16 KiB]); long-poll fallback /v1/poll.
- **IF-10-05 POST /v1/blobs/presign** (HTTPS JSON → S3/R2 presigned URL): Issues upload/download URLs for ciphertext blobs addressed by SHA-256.
- **IF-10-06 termax-sync::SyncEngine (start, push, pull, status, resolve_conflict)** (Rust API (shared desktop + mobile via termax-ffi)): Client sync engine shared by desktop and Flutter (FRB).
- **IF-10-07 /v1/sso/oidc/callback, /v1/sso/saml/acs** (OIDC (PKCE) / SAML 2.0): Business SSO via the system browser, returning to the app through loopback or an termax:// deep link.
- **IF-10-08 /v1/account/export, /v1/account (DELETE)** (HTTPS JSON): Server-side account data export and deletion request with waiting period.
- **IF-10-09 OTLP metrics/traces exporter** (OpenTelemetry): Allowlisted fields only (FR-CL02-014).
