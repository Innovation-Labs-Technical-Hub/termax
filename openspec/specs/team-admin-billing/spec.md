# team-admin-billing Specification

## Purpose

Define Termax's paid team layer: E2EE team vaults (vault keys sealed per member with X25519), RBAC, invite/revoke with key rotation, team-distributed MCP/approval policies, multiplayer session sharing with typist hand-off, plans and offline-verifiable signed entitlements, billing through a merchant of record, the admin console (P3) and the UI-11 screens in the desktop app.

Source: BRD-11 “Team vaults, multiplayer, admin & billing” v1.0 (draft) (2026-10-30). Modules: CL-03, CL-04, CL-05, CL-06, UI-11. Generated by `tools/openspec_from_brd.py`; edit through OpenSpec changes.

## Requirements

### Requirement: FR-CL03-001 Create a team vault with per-member sealed keys
The system SHALL provide: Create a team vault with per-member sealed keys.

Source: BRD-11 FR-CL03-001 · Module: CL-03 · Priority: Must · Phase: P2  
VI: Tạo team vault với key seal theo thành viên

#### Scenario: FR-CL03-001 specified behaviour
- **GIVEN** the system implements FR-CL03-001
- **THEN** Creating a vault generates a 256-bit vault key from the OS RNG on the creator's device, seals it to each member's X25519 public key (org membership key) with a sealed box, plus an Ed25519 signature by the sealer so recipients can verify provenance. Records in the vault are encrypted as in FR-CL02-001

#### Scenario: FR-CL03-001 acceptance 1
- **GIVEN** a 3-member team vault
- **WHEN** reading vault_memberships on the server
- **THEN** there are only 3 sealed keys and no other copy of the vault key

#### Scenario: FR-CL03-001 acceptance 2
- **GIVEN** a sealed key whose signature does not match the admin's public key in the directory
- **WHEN** a member receives it
- **THEN** the client refuses the key and shows 'Key origin could not be verified'

### Requirement: FR-CL03-005 Member revocation and vault key rotation
The system SHALL provide: Member revocation and vault key rotation.

Source: BRD-11 FR-CL03-005 · Module: CL-03 · Priority: Must · Phase: P2  
VI: Thu hồi thành viên và xoay vault key

#### Scenario: FR-CL03-005 specified behaviour
- **GIVEN** the system implements FR-CL03-005
- **THEN** Removing a member: the server cuts access immediately; the admin's client generates a new vault key, re-encrypts all records and blob references (large blobs re-encrypted in the background), seals the new key for remaining members and marks the old key retired. If the admin goes offline mid-way, rotation resumes at the next app start and a 'Rotating key' state is shown to other admins

#### Scenario: FR-CL03-005 acceptance 1
- **GIVEN** a 5,000-record vault
- **WHEN** a member is removed
- **THEN** rotation finishes within ≤60 s on the reference laptop and the removed member cannot fetch any record after ≤5 s

#### Scenario: FR-CL03-005 acceptance 2
- **GIVEN** the admin app is killed at 50 % of rotation
- **WHEN** reopened
- **THEN** rotation resumes from the checkpoint and no record lacks a valid key_id

### Requirement: FR-CL03-006 Credential exposure report after revocation

Source: BRD-11 FR-CL03-006 · Module: CL-03 · Priority: Should · Phase: P2

#### Scenario: FR-CL03-006 specified behaviour

#### Scenario: FR-CL03-006 acceptance 1

- **WHEN** a member is removed
- **THEN** the report lists exactly 12 items with the hosts using each

### Requirement: FR-CL04-002 E2EE between clients through the relay
The system SHALL provide: E2EE between clients through the relay.

Source: BRD-11 FR-CL04-002 · Module: CL-04 · Priority: Should · Phase: P2  
VI: E2EE giữa các client qua relay

#### Scenario: FR-CL04-002 specified behaviour
- **GIVEN** the system implements FR-CL04-002
- **THEN** The owner generates a 256-bit share key sealed to each participant's public key; every frame (output, input, resize, control event) is encrypted with XChaCha20-Poly1305 using per-sender counters for replay protection. The oxsync relay only routes by share_id. When someone leaves or is kicked, the share key rotates

#### Scenario: FR-CL04-002 acceptance 1
- **GIVEN** the relay records every frame of a shared session that runs 'echo CANARY123'
- **WHEN** scanning the capture
- **THEN** CANARY123 is not found

#### Scenario: FR-CL04-002 acceptance 2
- **GIVEN** the relay replays an old input frame
- **WHEN** the owner receives it
- **THEN** the frame is dropped because its counter did not increase

## Business rules

- **BR-11-01**: Vault keys are sealed only to member public keys; the server can never decrypt a team vault.
- **BR-11-02**: Viewers are read-only but can still read secrets (read access is cryptographic access); the UI must say so when assigning the role.
- **BR-11-03**: Every team vault always has ≥1 owner; the last owner cannot leave without transferring ownership.
- **BR-11-04**: Removing a member who could read secrets always includes vault key rotation in the same flow; it cannot be skipped.
- **BR-11-05**: Team policy: most restrictive wins — a team deny cannot be overridden by a personal allow; personal rules can only tighten.
- **BR-11-06**: Shared sessions: one typist at a time; the session owner can always take control back; viewers cannot send input.
- **BR-11-07**: Shared sessions never transmit auth prompts, passwords, passphrases or vault secrets; only the terminal stream.
- **BR-11-08**: Free features never depend on an entitlement; expiry only makes cloud features read-only after grace and never locks local data.
- **BR-11-09**: Prices follow ARCH-BRIEF §11 hypotheses: Pro ≈$10-12/mo, Team ≈$20/seat, Business ≈$30/seat (SSO included), Enterprise by contract; the product owner finalises before P2.
- **BR-11-10**: Admin actions are audited too; nobody (including owners) can delete or edit audit records.
- **BR-11-11**: A member's personal vaults are never visible to org admins.

## User journeys

### J-11-01 Create a team vault and invite teammates
1. The lead (Team plan) opens Team & Sync → Create vault 'Platform' and drags 40 hosts in from the personal vault (Copy or Move).
2. They invite 3 emails as members; each receives a link that expires in 7 days.
3. Invitees create an account/sign in; the lead sees 'Awaiting confirmation', optionally compares fingerprints and clicks Confirm.
4. The app seals the vault key to each member's public key; hosts appear on their machines within ≤1 s.

### J-11-02 Offboard a member
1. An admin selects the member → Remove from vault; the server denies all of their access within ≤5 s.
2. The admin's app rotates the vault key, re-encrypts records and seals the new key for the remaining members.
3. An exposure report lists the 12 credentials that person could read (passwords, private keys, tokens) with a 'Rotate credential' task button.
4. The removal, key rotation and credential list are written to the audit log.

### J-11-03 Pair-debug a production session
1. Engineer A, in pane 'api-prod-3', chooses Share session → invites B with Control rights.
2. B gets a notification and opens the session in view mode; the participant bar shows 'A typing · B viewing'.
3. B clicks Request control; A clicks Hand over; B types commands, A sees them live and can take control back with Mod+Shift+Enter.
4. A ends the share; the audit records time, participants and hand-offs.

### J-11-04 Business admin configures SSO, policy and SIEM (P3)
1. The admin signs in to the admin console with SSO + WebAuthn, verifies the domain via DNS TXT and enters Entra ID OIDC metadata.
2. They enable 'Enforce SSO' and organisation recovery with 2 admins.
3. They create a policy: external agents observe-only on prod-tagged hosts, MCP servers outside the allowlist blocked; roll out to 10 % of members, then 100 %.
4. They configure audit export to Splunk HEC; new events appear in Splunk within ≤5 minutes.

## Data entities

- **orgs**: id, name, plan, region, sso_connection_id, recovery_enabled, org_recovery_pub, created_at — One org per Team/Business/Enterprise customer.
- **member_keys**: account_id, org_id, x25519_pub, ed25519_pub, fingerprint, created_at, superseded_at — Public-key directory; history to detect changes.
- **team_vaults**: id, org_id, name_enc, current_key_id, rotating(bool), rotation_checkpoint, created_by, created_at — Vault name encrypted under the org key.
- **vault_memberships**: vault_id, account_id, role(owner|admin|member|viewer), key_id, sealed_vault_key, sealed_by, signature, state(invited|accepted|confirmed), created_at — Server checks roles; cannot open sealed_vault_key.
- **invites**: id, org_id, vault_id, email, role, token_hash, expires_at, accepted_at, revoked_at — Expire after 7 days.
- **policy_bundles**: org_id, version, ciphertext, signature, signed_by, rollout_percent, published_at — Rule content encrypted under the org key.
- **shares**: id, org_id, owner_device_id, host_ref_enc, mode(view|control), max_participants, started_at, ended_at — The relay knows only share_id and participants.
- **share_participants**: share_id, account_id, role(view|control), sealed_share_key, joined_at, left_at, kicked(bool) — Share key rotates when someone leaves.
- **subscriptions**: id, org_or_account_id, provider(paddle|stripe), provider_sub_id, plan, seats, status, trial_ends_at, period_end, dunning_until — Synced from MoR webhooks.
- **entitlements**: subject_id, payload_cbor, signature, key_id, issued_at, expires_at, grace_until — Ed25519; verified offline by clients.
- **invoices**: id, subscription_id, provider_ref, amount, tax, currency, pdf_url, issued_at — Issued by the MoR; Termax stores references only.
- **audit_events**: org_id, seq, prev_hash, hash, actor_id, action, target_ref, payload_enc, created_at — Hash chain; sensitive payload encrypted under the org audit key.
- **usage_daily**: org_id, date, seats_used, active_users, devices, shares, mcp_allow, mcp_ask, mcp_deny — Aggregates only.

- **IF-11-08 SIEM exporters: Splunk HEC, Datadog Logs, Elastic bulk, HTTPS webhook, S3 JSONL** (Outbound HTTPS): Cursor-based audit push with retry.
- **IF-11-09 /scim/v2** (SCIM 2.0): Provisioning from the IdP (P3, Should).
