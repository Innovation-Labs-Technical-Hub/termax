# platform-engineering Specification

## Purpose

Define the engineering platform that lets Termax build, test, sign, release and update safely across 6 desktop targets (Windows/macOS/Linux × amd64/arm64) plus mobile; quality gates (supply chain, fuzzing, perf, interop) that block releases violating ARCH-BRIEF §6 budgets; 2026-grade OS integration (DPI, dark mode, Wayland, IME, notifications, QoS/EcoQoS); and privacy-respecting observability/diagnostics (telemetry off by default).

Source: BRD-13 “Platform engineering: build, release, OS integration & observability” v1.0 (draft) (2026-10-30). Modules: PL-01, PL-02, PL-03, CO-13. Generated by `tools/openspec_from_brd.py`; edit through OpenSpec changes.

### Requirement: FR-PL02-008 Staged rollout, automatic halt and rollback
The system SHALL provide: Staged rollout, automatic halt and rollback.

Source: BRD-13 FR-PL02-008 · Module: PL-02 · Priority: Should · Phase: P1  
VI: Staged rollout, tự dừng và rollback

#### Scenario: FR-PL02-008 specified behaviour
- **GIVEN** the system implements FR-PL02-008
- **THEN** Manifests carry rollout_percent; clients pick a cohort from a locally stored random number (no identifier). Default schedule 1 → 10 → 50 → 100 % over 4 days; if the cohort's crash-free rate (from opt-in crash reports + store vitals) is < 99.5 % or a severe bug appears, the release manager or automation halts rollout and points the manifest to the previous version. - **GIVEN** a halted 10 % rollout
- **WHEN** a client outside the cohort checks
- **THEN** it does not get the new version; an in-cohort client that has not installed it yet does not either

## Business rules

- **BR-13-01**: The termax core and termax-mobile repos are public (Apache-2.0); termax-cloud is private and separate.
- **BR-13-02**: No GPL code is linked; cargo-deny allows only Apache-2.0, MIT, BSD-2/3, ISC, Zlib, Unicode-3.0, MPL-2.0 (MPL files unmodified or changes published); exceptions must be recorded by the tech lead in deny.toml.
- **BR-13-03**: Every released artifact on every channel is signed, with SHA-256 checksums, SBOM and provenance; nightly uses a key separate from stable.
- **BR-13-04**: Telemetry is off by default (D8). At startup there are no network calls except the update check (which can be disabled), and it sends only version, OS, arch and channel.
- **BR-13-05**: Only the OS RNG (getrandom/BCryptGenRandom/SecRandomCopyBytes) is used for keys, nonces and seeds; no entropy from child processes.
- **BR-13-06**: ARCH-BRIEF §6 performance budgets are release blockers; exceptions need tech-lead sign-off recorded in the repo with a fix-by date.
- **BR-13-07**: Signing keys never exist as files on runners; they are used only via signing services/cloud HSMs in protected environments with manual approval.
- **BR-13-08**: Diagnostics bundles and crash reports are created/sent only on explicit user action; no silent uploads.
- **BR-13-09**: Client-side russh advisories are patched and released within ≤72 h.

## User journeys

### J-13-01 Open a PR and get quality-gate feedback
1. An engineer pushes a branch and opens a PR against the termax repo.
2. CI runs build + tests on 6 targets in parallel, cargo-deny/audit/vet, 10-minute fuzzing, perf gates and an interop smoke against OpenSSH 10.x and Dropbear.
3. A bot comments a perf comparison (startup, RSS/tab, parser MB/s) against main; one metric is 7 % worse so the 'perf-gate' check fails.
4. The engineer fixes it and pushes; all checks pass within ≤25 minutes and the PR is merged.

### J-13-02 Ship a stable release with staged rollout
1. The release manager tags v1.2.0; the release workflow pauses at a protected environment awaiting approval.
2. After approval: Authenticode signing, DMG signing + notarisation + stapling, minisign/sigstore for Linux, SBOM and provenance generation, deltas from 1.1.x.
3. The stable manifest rolls out 1 % → 10 % → 50 % → 100 % over 4 days while cohort crash-free rates are watched.
4. On day 2 the 10 % cohort's crash-free rate drops to 99.2 %; rollout halts automatically, the manifest points back to 1.1.4 for users not yet updated, and patch 1.2.1 ships.

### J-13-03 A user sends a diagnostics bundle
1. A connection to a MikroTik switch fails; the user chooses 'Create diagnostics bundle' from the error overlay.
2. A preview lists the included files (24 h of logs, redacted config, version, OS, negotiated algorithms, matched quirks) with an option to mask host names/IPs.
3. The user saves the .zip and attaches it to an issue themselves; nothing is uploaded automatically.

### J-13-04 Patch a russh advisory within 72 hours
1. Daily cargo-audit reports a new client-side russh advisory; CI auto-opens a P0 issue.
2. The tech lead bumps russh and runs the full interop lab + extended fuzzing on the patch branch.
3. The patch ships on stable with a fast rollout (10 % → 100 % in 24 h) and security notes; total time ≤72 h.
