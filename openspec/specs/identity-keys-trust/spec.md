# identity-keys-trust Specification

## Purpose

Define the requirements for everything Termax must keep secret or must trust: the encrypted local vault (SQLite WAL + per-record XChaCha20-Poly1305, Argon2id + Secret Key key hierarchy), OS keychain/biometric unlock, SSH key management and the built-in agent, known hosts and the trust sheet, and the cross-cutting security architecture (STRIDE threat model, secret memory, crypto profiles, patch SLA, fuzzing, independent audit, disclosure policy).

Source: BRD-06 “Identity, keys, trust & vault security” v1.0 (draft) (2026-10-30). Modules: UI-07, CO-08, CO-09, CO-10, CO-14. Generated by `tools/openspec_from_brd.py`; edit through OpenSpec changes.

## Requirements

### Requirement: FR-UI07-001 Keychain screen: identities, keys, certificates
The system SHALL provide: Keychain screen: identities, keys, certificates.

Source: BRD-06 FR-UI07-001 · Module: UI-07 · Priority: Must · Phase: P1  
VI: Màn Keychain: identity, key, certificate

#### Scenario: FR-UI07-001 specified behaviour
- **GIVEN** the system implements FR-UI07-001

#### Scenario: FR-UI07-001 acceptance 1

#### Scenario: FR-UI07-001 acceptance 2

- **THEN** the confirmation lists the 3 hosts and an Undo toast is offered for 10 s after deletion

### Requirement: FR-CO08-002 Per-record XChaCha20-Poly1305 encryption
The system SHALL provide: Per-record XChaCha20-Poly1305 encryption.

Source: BRD-06 FR-CO08-002 · Module: CO-08 · Priority: Must · Phase: P1  
VI: Mã hoá từng record bằng XChaCha20-Poly1305

#### Scenario: FR-CO08-002 specified behaviour
- **GIVEN** the system implements FR-CO08-002
- **THEN** Each record payload is encrypted with the vault key using XChaCha20-Poly1305, a fresh random 192-bit nonce per write, and AAD = vault_id ‖ record_id ‖ type ‖ schema_version ‖ revision to prevent record swapping or replay. Hosts, labels, tags and paths also live in the payload; search uses an in-memory index built after unlock

#### Scenario: FR-CO08-002 acceptance 1
- **GIVEN** records A and B
- **WHEN** an attacker swaps A's ciphertext into B's row
- **THEN** decrypting B fails on AAD and the app reports a corrupt record instead of showing A's data

#### Scenario: FR-CO08-002 acceptance 2
- **GIVEN** a vault with host ‘db-prod-1’
- **WHEN** running strings/grep on the DB and WAL files
- **THEN** ‘db-prod-1’ is not found

### Requirement: FR-CO08-003 Key hierarchy: Argon2id + Secret Key (2SKD)
The system SHALL provide: Key hierarchy: Argon2id + Secret Key (2SKD).

Source: BRD-06 FR-CO08-003 · Module: CO-08 · Priority: Must · Phase: P1  
VI: Cây khoá: Argon2id + Secret Key (2SKD)

#### Scenario: FR-CO08-003 specified behaviour
- **GIVEN** the system implements FR-CO08-003
- **THEN** Master password → Argon2id (16-byte salt, parameters calibrated to 0.5-1.0 s, floor m=64 MiB, t=3) → combined with a device-generated 128-bit Secret Key via HKDF-SHA256 → Account Unlock Key (AUK) → unwraps the account key (256-bit symmetric key + an X25519 pair for later team vaults) → unwraps each vault's 256-bit vault key → record payloads. A password change only re-wraps the account key and does not re-encrypt records. KDF parameters are versioned so they can be upgraded

#### Scenario: FR-CO08-003 acceptance 1
- **GIVEN** an existing vault
- **WHEN** the master password changes
- **THEN** only the account-key record changes, zero records are rewritten and the vault opens with the new password

#### Scenario: FR-CO08-003 acceptance 2
- **GIVEN** an attacker holding the DB file but not the Secret Key
- **WHEN** brute-forcing the password
- **THEN** each guess requires both Argon2id and the unknown 128-bit Secret Key (verified by design review + test vectors)

## Business rules

- **BR-06-01**: No secret (password, passphrase, ProxyPassword, private key, BYOK API key, TOTP seed) is ever written to disk in plaintext: DB, WAL, temp files, logs, crash reports, exports (except a plain export the user explicitly chooses after a warning, which still excludes secrets).
- **BR-06-02**: Host-key checking cannot be disabled globally. The loosest setting is per-host ‘accept-new’; a stored key that changes is always blocked.
- **BR-06-03**: In every trust prompt the default, focused button is ‘Disconnect’; buttons are named by outcome (‘Trust & save’, ‘Connect once’, ‘Disconnect’), never Yes/No.
- **BR-06-04**: A changed host key is never accepted with a single keypress in the connect flow; replacing it needs a separate Known Hosts action with a second confirmation.
- **BR-06-05**: Termax never writes PPK2; it exports only OpenSSH (bcrypt-pbkdf) or PPK3 (Argon2id). It never generates DSA, RSA < 3072 or ECDSA keys with non-RFC 6979 nonces.
- **BR-06-06**: Forwarded sign requests always show the requester (forwarding host, jump chain, destination) and confirm-on-use is on by default.
- **BR-06-07**: External agents (MCP), plugins and LLM providers never receive private keys, passwords or secrets; at most public keys and fingerprints once permitted.
- **BR-06-08**: The vault locks automatically on OS screen lock/sleep and after a configurable idle time (default 30 minutes); locking wipes decryption keys from memory and also locks keys in the agent.
- **BR-06-09**: A client-reachable russh or crypto advisory must have a signed stable-channel release within ≤72 h of publication.

## User journeys

### J-06-01 First run: create the local vault and enable Touch ID
1. The user sets a master password; Termax rates strength inline and generates a 128-bit Secret Key.
2. Termax shows the Emergency Kit (Secret Key + instructions) to print or save as PDF and asks the user to confirm it is stored.
3. They enable ‘Unlock with Touch ID’; a device key is stored in the Keychain bound to biometrics.
4. The empty Keychain offers ‘Import ~/.ssh’; 3 keys import, one PPK2 key gets a weak-KDF warning with a suggestion to re-save as PPK3/OpenSSH.
5. They lock the vault and reopen it with Touch ID within ≤1 s.

### J-06-02 PuTTY migrant: PPKs, host keys and replacing Pageant
1. They import sessions from the PuTTY registry (BRD-02) with SshHostKeys; host keys become known hosts with source ‘PuTTY import’.
2. They import 2 PPK files; an ecdsa-sha2-nistp521 key gets a CVE-2024-31497 warning with a ‘Create replacement & Deploy’ button.
3. They enable the built-in agent with the Pageant-compatible endpoint (only when real Pageant is not running); WinSCP and old plink use keys from Termax.
4. They convert the remaining PPK2 key to PPK3 for legacy PuTTY tools, or OpenSSH for everything else.

### J-06-03 Host key changed while connecting
1. They connect to db-prod-1; the server key differs from the key stored since 2025-03-12.
2. The connection is blocked before any credential is sent; the incident sheet shows old/new SHA256 fingerprints, key type, first-seen/last-seen dates and both randomarts.
3. The default, focused button is ‘Disconnect’; Enter disconnects and the incident is recorded in the security event log.
4. After verifying with the infra team, the user opens Known Hosts, chooses ‘Replace key…’ and retypes the host name to confirm; the new key is stored with source ‘manual replace’.

### J-06-04 Agent forwarding with confirm-on-use through a bastion
1. Host app-7 uses ProxyJump via bastion-01 and forwards the agent only for key ‘github-deploy’, destination-constrained to github.com.
2. On app-7 the user runs git pull; the agent receives a forwarded sign request.
3. A prompt in the app chrome (not in the terminal) shows: key github-deploy, requested by app-7 via bastion-01, destination github.com, the destination host key SHA256; the user approves with Touch ID.
4. Another sign request to a destination outside the constraint is refused automatically and recorded in the security event log.

## Data entities

- **vaults**: id, kind(personal|team), schema_version, kdf_params(json), created_at, wrapped_vault_key (by account key) — Each vault has its own vault key; team vaults (BRD-11) wrap it per member.
- **account_keys**: id, salt, kdf_params, wrapped_account_key (by AUK), x25519_public, wrapped_x25519_private, created_at — AUK = HKDF(Argon2id(password), Secret Key); the Secret Key is never stored in the DB.
- **device_unlock**: id, platform, keychain_ref, wrapped_account_key (by device key), assurance(biometric_bound|consent_gated|none), created_at — The device key lives in the OS keychain; this record only holds the wrapped copy.
- **records**: id, vault_id, type, revision, created_at, updated_at, nonce, payload_ct, aad_version — Generic table for hosts, identities, keys, known hosts, snippets…; XChaCha20-Poly1305 payload.
- **ssh_keys (record type)**: algo, bits_or_curve, public_blob, fingerprint_sha256, comment, source, private_ct, flags(p521_cve, ppk2_origin), agent_policy(json), created_at, last_used_at — The private key always lives inside the encrypted payload.
- **certificates (record type)**: key_id_ref, cert_blob, ca_fingerprint, principals, valid_after, valid_before, critical_options, extensions — User certs attach to keys; host certs are handled through known_hosts CAs.
- **known_hosts (record type)**: pattern, port, key_type, key_blob, marker(none|cert_authority|revoked), source, pinned, hashed, first_seen, last_seen — In-memory index by host:port after unlock.
- **known_host_events**: id, known_host_ref, kind(added|replaced|incident|update_host_keys|removed), old_fp, new_fp, at, peer_ip — History for the Known Hosts drawer and incidents.
- **security_events**: seq, at, kind, subject_ref, detail(json, redacted), prev_hash, hash — Tamper-evident hash chain, sharing AG-03's audit-log mechanism.
- **schema_migrations**: version, applied_at, app_version, backup_ref — Migration log and the matching backup.

## Interfaces

- **IF-06-01 VaultService (termax-vault)** (Rust API): create, unlock(password|biometric), lock, get/put/query records, resolve(host), migrate, export/import .oxvault, change_password, rotate_secret_key.

- **IF-06-08 .oxvault file format** (File format (versioned)): Header: magic, version, KDF params, salt; body: XChaCha20-Poly1305 records; MAC'd manifest.

## Out of scope

- Cloud accounts, OPAQUE login, E2EE sync, cloud recovery kit (BRD-10) and team vaults with per-member key wrapping (BRD-11) — this BRD only defines the local key hierarchy they build on.
- SSH algorithm negotiation, strict-kex, trivial-auth refusal (CO-02, BRD-04); this BRD defines the crypto profiles CO-02 applies.
- PKCS#11/smart cards, GSSAPI/Kerberos (P3, BRD-04), certificate-issuing CA integrations (step-ca, Vault, Teleport) — reconsider after P2.
- General password-manager features (web logins, browser autofill).
