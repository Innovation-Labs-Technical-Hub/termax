# agentic-ai-mcp Specification

## Purpose

Specify Termax's agentic layer as three tightly coupled parts: (1) an in-app AI assistant acting as an MCP host on the user's own models (BYOK: Anthropic, OpenAI-compatible, local Ollama); (2) an Termax MCP server that lets external agents (Claude Desktop/Code, Cursor, Zed) read hosts, sessions and scrollback and, when granted, operate on servers; (3) a policy and approval engine that lives outside the model, decides deny > ask > allow, keeps approval inside Termax's own UI and writes a hash-chained audit log. Positioning: 'safe agent access to your servers', the main differentiator against Termius, Warp, Zed and the open-source SSH MCP servers.

Source: BRD-08 “Agentic: AI assistant, MCP server & approval policy” v1.0 (draft) (2026-10-30). Modules: UI-09, AG-01, AG-02, AG-03. Generated by `tools/openspec_from_brd.py`; edit through OpenSpec changes.

## Business rules

- **BR-08-01**: Decisions follow deny > ask > allow across all rule layers (built-in, team, host/tag, user, tool default); built-in rules cannot be lowered by the user, a team or a grant.
- **BR-08-02**: Every ask decision is approved only in Termax's own UI (desktop; paired mobile from P2). Elicitation responses, 'auto-approve' or any confirmation on the calling client never count as consent.
- **BR-08-03**: No secret (password, private key, passphrase, token, keyboard-interactive response, vault payload) leaves the vault through AI context, MCP tool results, resources, logs or audit records; hosts are referenced by opaque ID only.
- **BR-08-04**: External MCP clients are observe-only by default (D9). Operate needs an expiring per-host (optionally per-session) grant issued in Termax's UI (Pro tier, P2).
- **BR-08-05**: Hosts tagged prod: every agent-originated action that sends input, executes, writes files or opens a forward is ask; no rule, grant or 'approve for N min' turns it into allow.
- **BR-08-06**: Every AI- or agent-originated command runs where the user can see it (a visible pane or the Agent activity drawer) and carries a provenance marker in the chrome, distinct from server output and Termax messages (P4).
- **BR-08-07**: Terminal output and third-party MCP tool descriptions are untrusted data: sanitised, fenced and size-capped before reaching any model, and never able to change policy, grants or approvals.
- **BR-08-08**: MCP endpoints are local only: the stdio shim via the local control endpoint, or HTTP on loopback; configuring 0.0.0.0 or a LAN interface is impossible.
- **BR-08-09**: New code uses no deprecated MCP feature (Sampling, Roots, Logging, HTTP+SSE, new DCR); inference always calls the user's BYOK provider directly.
- **BR-08-10**: Every policy decision is written to the hash-chained audit log before the action executes (write-ahead); an action whose audit write fails does not run.
- **BR-08-11**: Tiering: Free includes AI BYOK, built-in tools, MCP observe, policy v1 and local audit; Pro adds MCP operate, approvals and mobile approval; Team adds team policies; Business adds audit export (ARCH-BRIEF §11).

## User journeys

### J-08-01 Explain an error with the in-app assistant (P1)
1. The staging-api pane prints 'nginx: [emerg] bind() to 0.0.0.0:443 failed (98: Address already in use)'.
2. The user selects the error, right-clicks → 'Ask AI about selection'; the panel opens (Mod+J) with the Selection and Host metadata chips attached; a 'Pane (last 200 lines)' chip is shown dimmed as a suggestion only.
3. The user opens 'What will be sent': provider, endpoint, model and payload with one span masked as '[REDACTED:token]', about 1.2k tokens.
4. Send; the answer streams in with a card 'sudo ss -ltnp | grep :443' whose risk 'read-only · sudo → low' is computed by AG-03.
5. The user clicks Run: the command is bracketed-pasted into the visible staging-api pane with an 'AI' gutter marker; the audit records actor=user, origin=assistant, decision=approved-by-click.

### J-08-02 External agent (Claude Code) observes a session (P1, observe-only)
1. The user runs 'claude mcp add termax -- tmx mcp'. On the first call the shim prints a 6-digit code to stderr and Termax shows a pairing sheet with the same code.
2. The user approves; the 'Claude Code' client receives a token with observe scope.
3. The agent calls list_hosts and receives id, label, tags and OS — no credentials.
4. The user toggles 'Share with agents' on the staging-api pane; the agent calls read_scrollback and receives sanitised output wrapped in an untrusted_terminal_output block with a nonce.
5. The agent calls run_command 'df -h' on the staging host: AG-03 classifies it read-only and allowlisted → allow; it runs on a separate exec channel, shown in the Agent activity drawer; the audit records the output hash.

### J-08-03 Operate request on prod held for approval (P2)
1. An agent with a 60-minute operate grant on prod-db-01 sends run_command 'sudo systemctl restart postgresql'.
2. AG-03: systemctl restart = medium, sudo raises it to high, prod host tag → ask; the grant cannot auto-allow.
3. The MCP server returns input_required with a URL elicitation termax://approvals/<id> and an HMAC-protected requestState; Termax raises an OS notification within 300 ms.
4. The user opens the sheet: exact bytes, host 'prod' (red + text), client, matched rule is the built-in prod-tag rule (FR-AG03-004); Approve arms after 1 s; the user picks Approve once.
5. The agent retries with requestState; the server checks the decision held in Termax (never the client's 'accept'), runs the command, returns exit code and sanitised output; the audit holds decision, approver and output hash.
6. Variant: the agent sends 'bash -c "$(echo cm0gLXJmIC8= | base64 -d)"' → dynamic command that cannot be analysed → ask with reason 'could not fully analyse'; a literal 'rm -rf /' is denied immediately with no prompt.

### J-08-04 Incident: kill switch and audit review (P1)
1. The user sees the status-bar chip 'Pending 4' climbing unusually fast from one client.
2. Click the chip → 'Stop all agents' (one click, no confirmation).
3. Within ≤1 s: all grants and session approvals are revoked, pending requests close as denied, running tasks receive SIGINT, the HTTP listener closes, stdio shims are disconnected; the chip shows 'Halted'.
4. Open the audit viewer, filter by client, click 'Verify chain' → OK; export redacted JSONL for the security team.
5. Revoke the client's token in Connected agents, then click Resume to re-enable other clients.
