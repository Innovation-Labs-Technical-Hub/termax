# automation-logging-cli Specification

## Purpose

Define the requirements for Termax's automation and traceability layer: snippets with variables, multi-step runbooks with checks and rollback, cross-session command history via OSC 133, a connection log replacing the Event Log, session logging with secret redaction by default, a recording timeline, and the tmx CLI sharing the app's vault so users (and scripts) can work outside the GUI.

Source: BRD-07 “Snippets, runbooks, history, logging & CLI” v1.0 (draft) (2026-10-30). Modules: UI-08, CO-12, PL-04. Generated by `tools/openspec_from_brd.py`; edit through OpenSpec changes.

## Business rules

- **BR-07-01**: Secrets are never displayed, logged, stored in history or sent to AI; snippet secret variables are resolved from the vault only at send time.
- **BR-07-02**: Every multi-host run, or any command the policy classifies as ‘ask’/destructive, must be confirmed with the host list and resolved commands; prod-tagged hosts always ask (AG-03); ‘deny’ commands are never sent.
- **BR-07-03**: Command history is opt-in, local-only by default, and honours exclusion rules (commands starting with a space, exclusion patterns).
- **BR-07-04**: Redaction is on by default for every log; input typed while echo is off (passwords, passphrases) is never logged, even when the user disables redaction for a host.
- **BR-07-05**: Log files append by default; overwriting an old file happens only on an explicit, outcome-labelled choice.
- **BR-07-06**: The CLI never accepts secrets via command-line arguments or environment variables; -pw is rejected with guidance; only a TTY prompt, --password-stdin, the OS keychain or an unlocked app are accepted.
- **BR-07-07**: The --json schema is versioned; breaking changes only happen in major versions.
- **BR-07-08**: Runbook rollback steps never run automatically; they always need user confirmation.

## User journeys

### J-07-01 Run a parameterised snippet on 5 staging hosts via broadcast
1. The user selects 5 hosts tagged staging, opens a broadcast group, presses Mod+; and picks snippet ‘restart-service’ (sudo systemctl restart {{service}}).
2. {{service}} takes the default ‘api’ from the staging group; a preview table shows the resolved command per host.
3. The policy engine classifies the command as ‘ask’ (systemctl restart); the confirmation lists the 5 hosts and the command, with a ‘Run on 5 hosts’ button.
4. The command runs in 5 visible panes; thanks to OSC 133 the summary shows 4 succeeded and 1 exited 5, linking to the failing pane.

### J-07-02 Troubleshoot an authentication failure with the connection log
1. Connecting to db-legacy fails; the pane banner shows code TMX-AUTH-004 and an ‘Open log’ button.
2. Mod+Shift+L opens the session's connection log; they filter level ≥ info, category auth.
3. The log shows server-sig-algs lacks rsa-sha2-*, the RSA key is refused, profile Modern.
4. They click ‘Ask AI about this’; the AI receives the redacted events and suggests enabling Legacy for this host only or using an Ed25519 key.
5. They export JSONL (redacted) to send to the infra team.

### J-07-03 A plink user's CI script moves to tmx
1. Old script: plink -load prod-db -batch -L 5432:localhost:5432 -N.
2. It becomes tmx ssh -load prod-db -batch -L 5432:localhost:5432 -N; -load maps to host prod-db imported from PuTTY.
3. The CI runner has no GUI app: tmx starts a headless runtime and unlocks the vault via --password-stdin from the CI secret store.
4. tmx scp --json -r build/ prod-db:/srv/app/ prints NDJSON progress; it exits 0 on success and 4 on a host-key mismatch.

### J-07-04 Run a database failover runbook (P2)
1. They open runbook ‘pg-failover’ with 6 steps, 2 confirmation gates and 1 rollback step; they choose primary and replica.
2. Step 1 runs pg_isready on an exec channel and checks the output contains ‘accepting connections’ — pass.
3. At the gate before promote, the runner shows the command, host and risk; the user confirms.
4. Step 5's replication-lag check fails; the runner stops and offers Retry / Rollback / Abort; the user picks Rollback and confirms the rollback step.
5. Run history stores redacted output; a Markdown export is attached to the incident ticket.

## Data entities

- **snippets (record type)**: name, description, body, target_shell, default_action(insert|run), variables[{name, type, default, raw}], scope(global|group|host), tags, favourite, last_used_at — Encrypted vault record; group/host-level defaults live on the group/host records.
- **runbooks (record type)**: name, version, inputs, roles, steps[{kind, command|snippet_ref, target_role, check{exit, regex, timeout}, rollback_ref}], created_by, updated_at — Each save creates a new version (P2).
- **runbook_runs (record type)**: runbook_ref, version, operator, started_at, finished_at, state, step_results[{step, host, state, exit, output_redacted, started_at, duration}] — Source for run history and Markdown export.
- **command_history (record type)**: host_ref, session_ref, command_redacted, cwd, exit_code, duration_ms, at — Opt-in, local; index only in memory after unlock.
- **connection_log_events**: seq, session_ref, at, level, category, code, message_key, fields(json, redacted) — Ring buffer + 7-day encrypted persistence; versioned JSON schema.
- **session_logs**: id, session_ref, host_ref, mode(printable|raw|packets|recording), path, encrypted, started_at, ended_at, bytes, gaps — Log file metadata; content lives in the file (encrypted inside the app folder).
- **log_policies (on host/group records)**: mode, timestamps, filename_template, folder, append, redaction{patterns, sftp_paths}, history_enabled, recording_enabled — Inherited App → Vault → Group → Host.
- **cli_clients**: id, name, binary_path, scopes, token_ref (keychain), paired_at, last_seen_at, revoked — Clients paired with the local control endpoint.
