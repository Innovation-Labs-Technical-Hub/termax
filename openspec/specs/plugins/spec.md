# plugins Specification

## Purpose

Specify Termax's plugin runtime: plugins are WASM components running on wasmtime 50.x in an in-process sandbox, calling the host through a versioned WIT world (termax:plugin/host@0.1.0), holding only the capabilities declared in their manifest and consented to by the user, bounded in CPU and memory, isolated on crash, with every action that touches hosts or sessions routed through the same policy and approval engine (AG-03) as MCP. Goal: let the community and teams extend Termax (themes, importers, palette commands, MCP tools, status-bar items, output decorators, protocol helpers) without adding new secret-leak paths or uncontrolled command execution.

Source: BRD-09 “Plugins & extensibility” v1.0 (draft) (2026-10-30). Modules: AG-04. Generated by `tools/openspec_from_brd.py`; edit through OpenSpec changes.

## Requirements

### Requirement: FR-AG04-001 WASM component runtime on wasmtime 50.x
The system SHALL provide: WASM component runtime on wasmtime 50.x.

Source: BRD-09 FR-AG04-001 · Module: AG-04 · Priority: Must · Phase: P2  
VI: Runtime WASM component trên wasmtime 50.x

#### Scenario: FR-AG04-001 specified behaviour
- **GIVEN** the system implements FR-AG04-001
- **THEN** The termax-plugin crate embeds wasmtime 50.x in-process and accepts only WASM components (core modules are rejected). Components are AOT-compiled with Cranelift at install time and cached as .cwasm keyed by (wasmtime version, CPU features, component hash). The pooling instance allocator is used. Plugins run on the plugin runtime's own worker threads, never the UI thread; host calls are async. wasmtime is upgraded within ≤72 h of a security advisory, mirroring the russh SLA

#### Scenario: FR-AG04-001 acceptance 1
- **GIVEN** a core wasm module (not a component)
- **WHEN** installing
- **THEN** it is rejected with 'component required'

#### Scenario: FR-AG04-001 acceptance 2
- **GIVEN** a plugin call in progress
- **WHEN** the UI thread is traced
- **THEN** no plugin frames appear on it

### Requirement: FR-AG04-002 Versioned WIT world with old worlds kept loadable
The system SHALL provide: Versioned WIT world with old worlds kept loadable.

Source: BRD-09 FR-AG04-002 · Module: AG-04 · Priority: Must · Phase: P2  
VI: WIT world có version, world cũ vẫn nạp được

#### Scenario: FR-AG04-002 specified behaviour
- **GIVEN** the system implements FR-AG04-002
- **THEN** WIT package termax:plugin, world host, starting at 0.1.0. The manifest declares api_version. The host embeds bindgen! for each supported world (current + the two previous 0.y versions, at least 12 months), like Zed's wasm_api_version mechanism; an adapter layer maps old worlds onto the new host implementation. A deprecation warning shows in the plugin list ≥6 months before a world is dropped. A plugin needing a newer world than the host → not loaded, with 'requires a newer Termax'

#### Scenario: FR-AG04-002 acceptance 1
- **GIVEN** a plugin built for world 0.1.0 and a host supporting up to 0.3.0
- **WHEN** loaded
- **THEN** it runs through the 0.1 adapter without a rebuild

#### Scenario: FR-AG04-002 acceptance 2
- **GIVEN** a plugin declaring api_version 0.9.0, newer than the host
- **WHEN** loading
- **THEN** it is not loaded and shows 'requires a newer Termax'

### Requirement: FR-AG04-004 Manifest permissions, capability imports and user consent
The system SHALL provide: Manifest permissions, capability imports and user consent.

Source: BRD-09 FR-AG04-004 · Module: AG-04 · Priority: Must · Phase: P2  
VI: Manifest quyền, import theo capability và đồng ý của người dùng

#### Scenario: FR-AG04-004 specified behaviour
- **GIVEN** the system implements FR-AG04-004
- **THEN** Manifest termax-plugin.toml: id (reverse-DNS), name, version, publisher, api_version, kinds, permissions, storage quota. Permission catalogue: ui.palette, ui.status-item, term.decorate (sanitised visible text of panes the user enables for the plugin + overlay drawing), term.read-output (sanitised output of shared sessions), hosts.read (metadata only), hosts.import (create/update hosts via a review sheet), files.picked (read only files the user picks in an OS dialog), vault.write-only (submit secrets to the vault, get back an opaque reference), mcp.provide-tools, exec.propose (submit commands/actions to AG-03), notify, storage (private KV, default 5 MiB, encrypted with the vault key), net.fetch (P3; declared host allowlist, HTTPS only). Each permission maps to a WIT interface linked only when granted; importing an undeclared interface → install fails; an optional permission the user declines → a stub returning permission_denied is linked. The consent sheet explains permissions in plain VI/EN with risk levels

#### Scenario: FR-AG04-004 acceptance 1
- **GIVEN** a plugin importing the hosts-import interface without declaring hosts.import
- **WHEN** installing
- **THEN** linking fails and the install is rejected naming the interface

#### Scenario: FR-AG04-004 acceptance 2
- **GIVEN** the user unticks the optional term.read-output permission
- **WHEN** the plugin calls that interface
- **THEN** it gets permission_denied and the plugin's other features keep working

### Requirement: FR-AG04-005 Resource limits: epoch, fuel, memory
The system SHALL provide: Resource limits: epoch, fuel, memory.

Source: BRD-09 FR-AG04-005 · Module: AG-04 · Priority: Must · Phase: P2  
VI: Giới hạn tài nguyên: epoch, fuel, bộ nhớ

#### Scenario: FR-AG04-005 specified behaviour
- **GIVEN** the system implements FR-AG04-005
- **THEN** Epoch interruption (1 ms tick) with per-call deadlines by kind: decorator/status item 5 ms, palette command 50 ms (then it may continue only asynchronously with progress), importer 30 s, MCP tool 30 s, protocol helper 2 ms per chunk. Fuel metering is enabled in devtools and tests for determinism. Memory per instance defaults to 64 MiB (manifest may request up to 256 MiB, with consent), tables ≤10,000 elements, 1 MiB stack, host-call arguments ≤1 MiB. Exceeding a limit → trap, result discarded, counted

#### Scenario: FR-AG04-005 acceptance 1
- **GIVEN** a decorator in an infinite loop
- **WHEN** called
- **THEN** it is interrupted within ≤6 ms (5 ms + 1 tick) and UI frame time is unchanged

#### Scenario: FR-AG04-005 acceptance 2
- **GIVEN** a plugin growing memory past 64 MiB without a granted increase
- **WHEN** run
- **THEN** the grow fails/traps and the error is written to the plugin log

### Requirement: FR-AG04-006 Crash isolation and supervision
The system SHALL provide: Crash isolation and supervision.

Source: BRD-09 FR-AG04-006 · Module: AG-04 · Priority: Must · Phase: P2  
VI: Cô lập crash và giám sát

#### Scenario: FR-AG04-006 specified behaviour
- **GIVEN** the system implements FR-AG04-006
- **THEN** A trap, limit breach or host-call misuse → the instance is discarded and the next call gets a fresh one; state is restored only from the plugin's storage. 3 failures in 10 minutes → the plugin is auto-disabled with a notice (Re-enable / Report). Safe mode starts with every plugin disabled. Crashes never kill a session or the app. Crash records (plugin id, version, trap kind, backtrace with no user data) are stored locally

#### Scenario: FR-AG04-006 acceptance 1
- **GIVEN** 1,000 forced traps across plugins
- **WHEN** the test runs
- **THEN** the app process stays alive and 0 sessions drop

#### Scenario: FR-AG04-006 acceptance 2
- **GIVEN** a plugin traps 3 times in 10 minutes
- **WHEN** the third occurs
- **THEN** the plugin is disabled and a notice appears

## Business rules

- **BR-09-01**: No ambient authority: a plugin can do only what the imports declared in its manifest and consented to by the user allow; no filesystem, network, environment variables or high-resolution clocks beyond those imports.
- **BR-09-02**: Plugins never receive vault secrets, private keys or unfiltered session I/O; terminal output given to a plugin always passes FR-AG03-011 sanitisation.
- **BR-09-03**: Every plugin action touching a host, session, file or forward goes through AG-03 with origin plugin:<id> and is audited; plugins propose, never execute directly.
- **BR-09-04**: Updates that add permissions or plugin kinds require fresh consent; permissions are never escalated silently.
- **BR-09-05**: Sideloaded/unsigned packages install only after an explicit warning, carry an 'Unverified' badge and expose no tools to external MCP clients unless the user enables it for that plugin.
- **BR-09-06**: Plugin code never runs on the UI thread; a plugin cannot block rendering or input.
- **BR-09-07**: The kill switch (FR-AG03-015) also halts plugin-originated actions; a safe mode starts with all plugins disabled ('termax --safe-mode').
- **BR-09-08**: Data-only packages (themes, keymaps, snippet packs) contain no code and need no execution rights.
- **BR-09-09**: Tiering: the plugin preview (P2) is in every tier including Free; team-managed allowlists belong to Team/Business; distribution via the admin console is P3.

## User journeys

### J-09-01 Install a curated plugin from the registry
1. Settings › Plugins › Browse, search 'kube-context'; the detail page shows publisher 'Verified', version, api_version 0.1.0, source repo and the permission list.
2. Click Install: a consent sheet lists, in plain language, ui.status-item, hosts.read, mcp.provide-tools and exec.propose with risk levels.
3. The user consents; Termax verifies the publisher signature and the registry index signature, AOT-compiles and caches the component.
4. The status bar shows a 'ctx: staging-eu' item; the plugin:kube-context:get_context tool appears to the assistant with default permission confirm.

### J-09-02 Developer builds a plugin with the SDK and hot reload
1. Run 'cargo termax-plugin new hello --kind command' to scaffold a project using termax-plugin-sdk.
2. Run 'tmx plugin dev ./hello'; the 'Hello: greet host' command appears in the palette (Mod+Shift+P).
3. Edit and rebuild; the plugin reloads within ≤2 s and the console shows logs and per-call timing.
4. 'tmx plugin validate' confirms imports match the manifest; 'tmx plugin pack --sign' signs with the publisher key; submit to the registry for review.

### J-09-03 A plugin MCP tool proposes a command through policy
1. The assistant calls plugin:db-helper:slow_queries for host prod-db-01 (the user has confirmed the tool).
2. The plugin calls exec.propose with 'psql -c "select * from pg_stat_statements order by total_exec_time desc limit 10"'.
3. AG-03 evaluates origin=plugin:db-helper, prod host tag → ask; the request enters the approval queue labelled 'Plugin: db-helper (Verified)'.
4. The user approves; the command runs on an exec channel, sanitised output goes back to the plugin (which holds term.read-output) and then to the model; the audit records both plugin and assistant.

### J-09-04 Sideloading an unsigned plugin that gets auto-disabled
1. The user drags an .oxtpkg file into Settings › Plugins; a red 'Unverified publisher' warning dialog lists the permissions.
2. The user installs it; the plugin carries an 'Unverified' badge and cannot expose tools to external MCP clients.
3. The plugin's decorator exceeds its epoch budget 3 times in 10 minutes; each time the instance is discarded and UI frames are unaffected.
4. Termax auto-disables the plugin with a toast 'kube-colors was disabled after 3 failures' offering Re-enable / Report; sessions keep running.

## Out of scope

- Native (dylib/so) plugins, Node/JS plugins with ambient authority, and arbitrary webviews or UI panels (following Zed's precedent) in P2.
- Plugins that replace or hook the SSH transport, crypto, authentication or the vault.
- Paid plugin marketplace and revenue share; plugins on mobile in P2 (see Q-09-02).
- Extism or a core-wasm + host-function model as the primary API.
