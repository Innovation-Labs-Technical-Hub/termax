# connectivity Specification

## Purpose

Define requirements for everything between the user and the remote machine: the one-process, many-session runtime (registry, lifecycle, reconnect with backoff, Duplicate as a new channel, local control endpoint for CLI and MCP, headless mode); SSH transport and authentication on a russh facade with profile-based crypto policy (ML-KEM hybrid first, strict-kex, rsa-sha2, AEAD, PuTTY-style warn-below line); ProxyJump, proxies, quirks; channels and forwarding (-L/-R/-D/streamlocal, agent forwarding with confirmation, X11, keepalive with want-reply, special commands, connection sharing); other protocols (Telnet, Serial, Raw, local shell, ldisc, Mosh/ET) and the port forwarding manager. Goals: fast connections that are secure by default, Duplicate ≤20 ms + network, ≥2 MiB initial window, and no network or crypto work on the UI thread.

Source: BRD-04 “Connectivity: session runtime, SSH, forwarding & other protocols” v1.0 (draft) (2026-10-30). Modules: CO-01, CO-02, CO-03, CO-07, UI-06. Generated by `tools/openspec_from_brd.py`; edit through OpenSpec changes.

## Requirements

### Requirement: FR-CO01-001 One-process, many-session runtime
The system SHALL provide: One-process, many-session runtime.

Source: BRD-04 FR-CO01-001 · Module: CO-01 · Priority: Must · Phase: P1  
VI: Runtime một tiến trình, nhiều session

#### Scenario: FR-CO01-001 specified behaviour
- **GIVEN** the system implements FR-CO01-001
- **THEN** termax-core runs one dedicated multi-threaded tokio runtime (2 I/O workers by default, configurable) for every session in the desktop process. The UI thread never does socket I/O, crypto, DNS or parsing. One timer wheel per process, no periodic ticks. KEX, signing, DH-GEX bignums and key decryption (Argon2/bcrypt) run on the blocking pool. I/O uses IOCP/kqueue/epoll via mio (no 63-handle WaitForMultipleObjects limit)

#### Scenario: FR-CO01-001 acceptance 1
- **GIVEN** 50 SSH sessions in one window
- **THEN** there is one Termax process and the number of I/O threads does not grow with the session count

#### Scenario: FR-CO01-001 acceptance 2
- **GIVEN** an 8192-bit DH-GEX KEX with a slow server
- **THEN** the UI thread is never blocked for more than 4 ms (tracing) and other tabs stay responsive

### Requirement: FR-CO01-002 Session registry
The system SHALL provide: Session registry.

Source: BRD-04 FR-CO01-002 · Module: CO-01 · Priority: Must · Phase: P1  
VI: Session registry

#### Scenario: FR-CO01-002 specified behaviour
- **GIVEN** the system implements FR-CO01-002
- **THEN** Each session has a stable SessionId (UUIDv7), host_id or ad-hoc target, protocol, connection_id, channels, state, created/opened times, bound panes, owning client (UI/CLI/MCP/headless) and grants (observe/operate). A list/subscribe API emits StateChanged, Title, Cwd, Bell and Exit events. The registry feeds the Sessions rail item, `tmx ls` and the MCP list_sessions tool

#### Scenario: FR-CO01-002 acceptance 1
- **GIVEN** 3 tabs and 1 attached CLI client
- **WHEN** session.list is called on the local control endpoint
- **THEN** 3 sessions are returned with state, host, protocol and connection_id, and the CLI client is recorded on its session

#### Scenario: FR-CO01-002 acceptance 2
- **GIVEN** a session changes state
- **THEN** every subscriber receives StateChanged within ≤50 ms

### Requirement: FR-CO01-003 Lifecycle state machine and stable error codes
The system SHALL provide: Lifecycle state machine and stable error codes.

Source: BRD-04 FR-CO01-003 · Module: CO-01 · Priority: Must · Phase: P1  
VI: Máy trạng thái vòng đời và mã lỗi ổn định

#### Scenario: FR-CO01-003 specified behaviour
- **GIVEN** the system implements FR-CO01-003
- **THEN** States: Idle → Resolving → Connecting (TCP/proxy/jump) → Handshaking (version, KEX, host key) → Authenticating → Open → Stalled (missed keepalive) → Disconnected(reason) → Reconnecting → Closed. Every Disconnected carries a stable TMX-<area>-<code> error code, a VI/EN message, technical detail and suggested actions; every code has a doc page. All transitions go to the connection log. No modal dialogs for errors

#### Scenario: FR-CO01-003 acceptance 1
- **GIVEN** the server refuses the TCP connection
- **THEN** the session enters Disconnected with a stable code (e.g. TMX-NET-002), a VI/EN message and suggested actions, with no modal dialog

#### Scenario: FR-CO01-003 acceptance 2
- **GIVEN** the error-code catalogue
- **THEN** every code has a VI/EN doc page (CI checks the links)

### Requirement: FR-CO01-004 Auto-reconnect with backoff
The system SHALL provide: Auto-reconnect with backoff.

Source: BRD-04 FR-CO01-004 · Module: CO-01 · Priority: Must · Phase: P1  
VI: Auto-reconnect có backoff

#### Scenario: FR-CO01-004 specified behaviour
- **GIVEN** the system implements FR-CO01-004
- **THEN** For transient failures (network error, keepalive timeout, server close without an auth error): reconnect with exponential backoff and jitter 1, 2, 4, 8, 16, 32 s, capped at 60 s; 10 attempts by default (configurable or unlimited); an immediate attempt on network-change/resume. Restores pty size, env, auto-start forwards and the agent-forwarding setting. Re-auth is silent when credentials are non-interactive (agent, key in an unlocked vault), otherwise prompted in chrome. Never auto-reconnects after an auth failure, host-key mismatch, user disconnect or ‘too many authentication failures’

#### Scenario: FR-CO01-004 acceptance 1
- **GIVEN** the network drops for 10 s and returns (netem)
- **THEN** the session reconnects within ≤1 backoff step after the network returns, auto-start forwards are restored and the pane shows ‘Reconnected’

#### Scenario: FR-CO01-004 acceptance 2
- **GIVEN** the failure is a changed host key
- **THEN** there is no automatic retry and the trust sheet opens

#### Scenario: FR-CO01-004 acceptance 3
- **GIVEN** 3 consecutive attempts
- **THEN** the waits follow 1 s, 2 s, 4 s (±jitter) and the overlay shows the attempt number

### Requirement: FR-CO01-005 Duplicate = new channel on the existing connection (H6)
The system SHALL provide: Duplicate = new channel on the existing connection (H6).

Source: BRD-04 FR-CO01-005 · Module: CO-01 · Priority: Must · Phase: P1  
VI: Duplicate = kênh mới trên kết nối sẵn có (H6)

#### Scenario: FR-CO01-005 specified behaviour
- **GIVEN** the system implements FR-CO01-005
- **THEN** Mod+Shift+T / ‘Duplicate’ opens a new session channel (pty + shell) on the authenticated connection with no new KEX or auth. Local overhead ≤20 ms, plus at most 2 RTT (channel open, then pipelined pty-req/shell). It copies the session's live settings (profile, env, including unsaved overrides). If the channel open fails (MaxSessions, ‘administratively prohibited’), a new connection is opened automatically with an explanatory toast. An explicit ‘Duplicate as new connection’ option exists. SFTP (Mod+E) also uses a new subsystem channel on the same connection

#### Scenario: FR-CO01-005 acceptance 1
- **GIVEN** an authenticated SSH session
- **WHEN** Mod+Shift+T is pressed
- **THEN** the new pane has the same connection_id, no new KEX/auth happens and local overhead is ≤20 ms (tracing) plus at most 2 RTT

#### Scenario: FR-CO01-005 acceptance 2
- **GIVEN** the server has reached MaxSessions
- **WHEN** Duplicate is used
- **THEN** Termax opens a new connection, shows an explanatory toast and the pane is still created

### Requirement: FR-CO01-006 Local control endpoint
The system SHALL provide: Local control endpoint.

Source: BRD-04 FR-CO01-006 · Module: CO-01 · Priority: Must · Phase: P1  
VI: Local control endpoint

#### Scenario: FR-CO01-006 specified behaviour
- **GIVEN** the system implements FR-CO01-006
- **THEN** Unix: a UDS in the user's runtime directory (e.g. $XDG_RUNTIME_DIR/termax/control.sock; under Application Support on macOS, mindful of path-length limits), directory 0700, socket 0600, peer UID checked (SO_PEERCRED/getpeereid). Windows: named pipe ‘termax-control-<SID hash>’ with a DACL granting only the current user's SID, PIPE_REJECT_REMOTE_CLIENTS, client process checked. Per-client tokens: each client (tmx, tmx mcp) pairs once, the user approves in the UI, tokens live in the OS keychain with observe/operate scopes. Length-framed JSON-RPC 2.0 with api_version, rate limits, and every call audited (AG-03)

#### Scenario: FR-CO01-006 acceptance 1
- **GIVEN** a different user account on the same machine
- **WHEN** it connects to the socket/pipe
- **THEN** the OS refuses it (0600/DACL) and the event is logged

#### Scenario: FR-CO01-006 acceptance 2
- **GIVEN** a client without a token
- **WHEN** it calls session.list
- **THEN** it gets unauthorized; after the user approves pairing, the same call succeeds with the observe scope

#### Scenario: FR-CO01-006 acceptance 3
- **GIVEN** an observe-only token
- **WHEN** session.send_input is called
- **THEN** it is refused with TMX-CTL-403 and an approval request is created if policy allows

### Requirement: FR-CO01-007 Headless mode
The system SHALL provide: Headless mode.

Source: BRD-04 FR-CO01-007 · Module: CO-01 · Priority: Should · Phase: P1  
VI: Headless mode

#### Scenario: FR-CO01-007 specified behaviour

#### Scenario: FR-CO01-007 acceptance 2
- **GIVEN** a headless runtime with no sessions or clients for 5 minutes
- **THEN** the process exits and removes its socket

### Requirement: FR-CO01-008 Network-change and sleep/wake handling
The system SHALL provide: Network-change and sleep/wake handling.

Source: BRD-04 FR-CO01-008 · Module: CO-01 · Priority: Must · Phase: P1  
VI: Xử lý đổi mạng và sleep/wake

#### Scenario: FR-CO01-008 specified behaviour
- **GIVEN** the system implements FR-CO01-008
- **THEN** Subscribe to OS network-change events (macOS NWPathMonitor, Windows NotifyIpInterfaceChange/NLM, Linux netlink/NetworkManager D-Bus) and resume events. #### Scenario: FR-CO01-008 acceptance 2
- **GIVEN** a resume with 20 sessions
- **THEN** at most 4 handshakes run in parallel

### Requirement: FR-CO02-002 Algorithm policy profiles and ‘warn below’ UX
The system SHALL provide: Algorithm policy profiles and ‘warn below’ UX.

Source: BRD-04 FR-CO02-002 · Module: CO-02 · Priority: Must · Phase: P1  
VI: Profile chính sách thuật toán và UX ‘warn below’

#### Scenario: FR-CO02-002 specified behaviour
- **GIVEN** the system implements FR-CO02-002
- **THEN** Three built-in profiles plus custom; each list (KEX, host key, cipher, MAC, compression) is ordered with a PuTTY-style ‘warn below’ line. Modern (default): KEX mlkem768x25519-sha256, curve25519-sha256 (+@libssh.org), diffie-hellman-group16/18-sha512; ciphers aes256-gcm/aes128-gcm@openssh.com, chacha20-poly1305@openssh.com, aes256/128-ctr; MACs hmac-sha2-512/256-etm; host keys ssh-ed25519, ecdsa-sha2-nistp256/384/521, rsa-sha2-512/256 (with cert variants). Compat adds ecdh-sha2-nistp*, diffie-hellman-group-exchange-sha256 (minimum 2048, preferred 3072 bits), group14-sha256, non-ETM hmac-sha2. Legacy (per host only) adds group14-sha1, group1-sha1, dh-gex-sha1, aes-cbc, 3des-cbc, hmac-sha1, ssh-rsa SHA-1, all below the line. Negotiating a below-the-line algorithm shows a consent sheet (algorithm, reason, ‘Allow for this host’/‘Cancel’) before auth; consent is stored per host and the status bar always shows a badge. Profiles inherit App→Vault→Group→Host. The connection log records the negotiated algorithms

#### Scenario: FR-CO02-002 acceptance 1
- **GIVEN** a new host on the default profile
- **WHEN** connecting to OpenSSH 10.x
- **THEN** nothing below the line is negotiated and the connection log records KEX/cipher/MAC/host key

#### Scenario: FR-CO02-002 acceptance 2
- **GIVEN** a device offering only diffie-hellman-group1-sha1 and aes128-cbc
- **WHEN** connecting with the modern profile
- **THEN** it stops before auth with ‘no common algorithm’ and suggests legacy for this host only

#### Scenario: FR-CO02-002 acceptance 3
- **GIVEN** a legacy host where the server picks 3des-cbc
- **THEN** the consent sheet names the algorithm and reason; ‘Allow for this host’ stores consent and the status bar shows a warning badge

### Requirement: FR-CO02-004 Strict KEX against Terrapin (S1)
The system SHALL provide: Strict KEX against Terrapin (S1).

Source: BRD-04 FR-CO02-004 · Module: CO-02 · Priority: Must · Phase: P1  
VI: Strict KEX chống Terrapin (S1)

#### Scenario: FR-CO02-004 specified behaviour
- **GIVEN** the system implements FR-CO02-004
- **THEN** Always advertise kex-strict-c-v00@openssh.com; when the server has kex-strict-s, enforce strict mode (sequence numbers reset at NEWKEYS, abort on unexpected packets during the first KEX). If the server lacks strict-kex and negotiation yields chacha20-poly1305 or an -etm MAC (Terrapin-exposed combinations): the modern profile aborts and retries once with a safe proposal (AES-GCM, or AES-CTR + non-ETM MAC), logging why; if no safe combination exists it stops with an explanation. Compat/legacy profiles show a warning sheet. A conformance test injects IGNORE before NEWKEYS

#### Scenario: FR-CO02-004 acceptance 1
- **GIVEN** a strict-kex server
- **WHEN** the fixture injects SSH_MSG_IGNORE before NEWKEYS
- **THEN** Termax aborts with the stable code TMX-SSH-STRICTKEX

#### Scenario: FR-CO02-004 acceptance 2
- **GIVEN** a server without strict-kex that negotiates chacha20-poly1305
- **WHEN** using the modern profile
- **THEN** Termax retries once with a safe proposal; if the server has no AES-GCM/CTR it stops and explains the Terrapin risk

### Requirement: FR-CO02-005 rsa-sha2 and server-sig-algs (S3)
The system SHALL provide: rsa-sha2 and server-sig-algs (S3).

Source: BRD-04 FR-CO02-005 · Module: CO-02 · Priority: Must · Phase: P1  
VI: rsa-sha2 và server-sig-algs (S3)

#### Scenario: FR-CO02-005 acceptance 2
- **GIVEN** a server without server-sig-algs and a non-legacy host
- **THEN** Termax never sends an ssh-rsa SHA-1 signature

### Requirement: FR-CO02-006 Hardware-aware AEAD preference, CBC legacy-only (H9, H10)
The system SHALL provide: Hardware-aware AEAD preference, CBC legacy-only (H9, H10).

Source: BRD-04 FR-CO02-006 · Module: CO-02 · Priority: Must · Phase: P1

#### Scenario: FR-CO02-006 specified behaviour
- **GIVEN** the system implements FR-CO02-006

#### Scenario: FR-CO02-006 acceptance 2
- **GIVEN** the modern or compat profile
- **THEN** the client KEXINIT contains no *-cbc algorithm (checked in the packet log)

### Requirement: FR-CO02-007 Authentication method orchestration

#### Scenario: FR-CO02-007 acceptance 2
- **GIVEN** a server requiring publickey then keyboard-interactive (partial success)
- **THEN** both steps complete within one connection

### Requirement: FR-CO02-010 Trivial-auth refusal (S6)
The system SHALL provide: Trivial-auth refusal (S6).

## Business rules

- **BR-04-01**: No protocol or crypto code is ported from PuTTY; PuTTY 0.74 is a behaviour reference and test-vector source only.
- **BR-04-02**: Host-key verification (CO-10) must complete before any credential is sent; a changed key is a hard stop with no auto-reconnect.
- **BR-04-03**: The modern profile is the default for new hosts; legacy is set per host only, never app-wide; any algorithm below the warn line needs per-host consent and always shows a badge.
- **BR-04-04**: Passwords, proxy passwords and passphrases come only from the vault/keychain or a prompt; never plaintext on disk or in logs.
- **BR-04-05**: Agent forwarding is off by default; when on, each forwarded signature needs confirmation unless the user opts out per host; prod-tagged hosts always confirm.
- **BR-04-06**: Forward listeners bind to loopback by default; binding beyond loopback needs explicit confirmation and shows an ‘Exposed to network’ badge.
- **BR-04-07**: Telnet and Raw always show a ‘Not encrypted’ badge; vault passwords are never auto-typed into plaintext sessions.
- **BR-04-08**: External clients (CLI, MCP) on the local control endpoint are observe-only by default; operate needs an expiring grant (AG-02/AG-03).
- **BR-04-09**: Auto-reconnect never retries after an auth failure, a host-key mismatch or a user-initiated disconnect.
- **BR-04-10**: No GPL code is linked; Mosh runs only as an external mosh-client process.

## User journeys

### J-04-01 Reaching a prod DB through 2 bastions with an automatic tunnel
1. Press Mod+K, type ‘db-prod’, Enter; the host is configured with ProxyJump bastion-1 → bastion-2.
2. Each hop's host key is checked against known hosts; a new hop shows the trust sheet for that hop.
3. Authentication uses a FIDO2 key in the agent: a ‘Touch your security key’ sheet appears in chrome.
4. The auto-start -L 5432 rule turns Listening; the status bar shows the PQ badge, a ‘1 forward’ chip and ‘via bastion-1 → bastion-2’.
5. psql to localhost:5432 connects; the Port Forwarding screen shows 1 active connection.

### J-04-02 Duplicating a tab, then the laptop sleeps and wakes
1. Press Mod+Shift+T: a new pane opens on the same connection with no new KEX/auth.
2. Close the lid; on reopening the OS reports resume and a network change.
3. The runtime probes every connection with keepalive@openssh; dead ones go Stalled, then Disconnected.
4. Auto-reconnect follows the 1 s, 2 s, 4 s backoff with at most 4 parallel handshakes.
5. Once reconnected, both panes show a ‘Reconnected’ line and auto-start forwards are restored.

### J-04-03 Network engineer: serial console and a legacy SSH device
1. Plug in a USB-serial cable; the picker lists ‘FTDI FT232R (COM5)’ with VID:PID; choose 9600 8N1.
2. Reboot the switch and choose ‘Send ▸ Break’ to enter ROMMON.
3. Open SSH to an old router offering only diffie-hellman-group14-sha1 and aes128-cbc; the modern profile reports ‘no common algorithm’ and suggests legacy for this host only.
4. Switch the host to legacy; the warning sheet lists the below-the-line algorithms; choose ‘Allow for this host’.
5. That host's status bar shows a warning badge; other hosts stay on modern.

### J-04-04 An external agent attaches to a session via the local control endpoint
1. Configure Claude Code to use `tmx mcp`; on first use the shim requests pairing and Termax shows an approval for the new client.
2. Approve with the observe scope; the agent calls list_sessions and reads sanitised scrollback.
3. The agent asks to send_signal INT to a hung pane; since the token is observe-only, the request goes into Termax's approval queue.
4. The user approves once; the signal is sent on the channel and written to the audit log.

## Data entities

- **sessions**: id (UUIDv7), host_id|null, adhoc_target, protocol(ssh|telnet|serial|raw|local|mosh|et), connection_id, state, pane_id, client_kind(ui|cli|mcp|headless), started_at, opened_at, ended_at, end_code, reconnect_attempts — Runtime registry; a summary row (no content) is persisted to CO-12 history.
- **connections**: id, key_hash(host, port, user, identity_id, jump_chain, profile_id), server_version, kex, cipher, mac, hostkey_alg, hostkey_fp_sha256, pq(bool), strict_kex(bool), quirks[], hops[], rtt_ms, channels_open, opened_at, last_keepalive_at — Runtime only; a snapshot goes to the connection log.
- **port_forwards**: id, host_id, kind(L|R|D|SL), bind_addr, bind_port|bind_path, dest_host, dest_port|dest_path, auto_start, keep_alive, template_id, enabled, exposed_confirmed_at, created_at, updated_at — Stored in the vault, synced from P2; live state is runtime.
- **proxy_profiles**: id, vault_id, name, kind(socks4|socks4a|socks5|http|command), host, port, username, secret_ref, command_template, dns_mode(local|remote), created_at, updated_at — secret_ref points to an encrypted vault record; there is no plaintext password field.
- **jump_hops**: host_id, position, jump_host_id|adhoc_target, profile_id — Ordered ProxyJump chain; edited in the BRD-02 host editor.
- **crypto_profiles**: id, name(modern|compat|legacy|custom), kex[], hostkey[], cipher[], mac[], compression[], warn_after{list: index}, built_in(bool) — Built-in profiles are read-only; custom profiles inherit App→Vault→Group→Host.
- **algorithm_consents**: host_id, category, algorithm, granted_at, device_id — Per-host consent for below-the-line algorithms.
- **quirks**: id, match(server version regex), flags[], mode(auto|on|off), source(builtin|user), host_id|null, notes — Built-in table embedded in the binary; user overrides stored in the vault.
- **serial_profiles**: host_id, device_match(vid, pid, serial | path), baud, data_bits, parity, stop_bits, flow, break_ms, dtr, rts, ldisc_mode, line_ending — Attributes of a Serial-type host.
- **control_clients**: id, name, kind(cli|mcp|plugin), process_path, token_hash, scopes(observe|operate), created_at, last_seen_at, revoked_at — The raw token lives only in the OS keychain; the DB keeps a hash.
