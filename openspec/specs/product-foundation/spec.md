# product-foundation Specification

## Purpose

This document sets out the business goals, scope, personas, release plan, constraints, assumptions and the common non-functional requirements (NFR-00-xxx) for Termax, a Termius-class SSH workspace rebuilt from scratch in Rust. Every BRD-01…BRD-13 inherits these common NFRs and may only add to or tighten them, never relax them. It is the entry point for the product owner, engineering, design and partners when they evaluate, prioritise and accept the project.

Source: BRD-00 “Project overview, scope & common requirements” v1.0 (draft) (2026-10-30). Modules: cross-cutting. Generated by `tools/openspec_from_brd.py`; edit through OpenSpec changes.

## Business rules

- **BR-00-01**: Local-first: every Free feature works fully with no account and no network; paid features are cloud/team services only, with no artificial limits on hosts, tabs or SFTP.
- **BR-00-02**: Secrets (passwords, passphrases, private keys, BYOK tokens) never leave the device unencrypted and are never sent to an LLM, MCP client or plugin.
- **BR-00-03**: Every non-read-only agent action (in-app or external) goes through the deny > ask > allow policy engine; approval is only given in Termax's own UI, never trusted from the calling agent.
- **BR-00-04**: No PuTTY protocol/crypto code is copied or ported; PuTTY 0.74 is a behaviour reference and test-vector source only, and any reused asset carries MIT-style attribution.
- **BR-00-05**: Every user-facing string and every product document ships in both VI and EN.
- **BR-00-06**: PuTTY/Termius names and logos do not appear in product UI; mockups are only “inspired by” the layouts. The only exception, pending legal confirmation, is a plain-text import-source label (see Q-00-07).

## Constraints

- Apache-2.0 for the core and app; the cloud service (oxsync, admin console) is closed source in a separate repo.
- Dependencies must be Apache/MIT/BSD/MPL-2.0 compatible (MPL files kept unmodified or changes published); no GPL code is linked: Zed's terminal/agent crates are GPL-3.0 and cannot be copied, mosh is GPL-3.0 and is only run as an external process. cargo-deny enforces this in CI.
- No PuTTY protocol/crypto code is ported (no strict-kex, P-521 nonce bias, 9 CVE-tracked fixes missing after 0.74).
- Team of 3-5 devs (MVP 4.5 FTE: tech lead/core-SSH, UI lead, terminal/render, AI from month 2, platform/security 0.5), designer 0.5; cloud backend from month 5, Flutter from month 8.
- Branding: “Termax” is a provisional codename, not trademark-checked (D3); no PuTTY or Termius names/logos in the UI.
- Linux uses wgpu and needs Vulkan 1.3; a fallback renderer is required for VMs, older iGPUs and remote desktops.
- russh ≥0.65 (floor 0.64.1) behind the `termax-ssh` facade; ≤72 h upgrade SLA for client-reachable advisories.
- Budget: CI is free because the repo is public; Apple Developer $99/year; the Windows signing path for a Vietnamese entity is unresolved (D4).

## User journeys

### J-00-01 A PuTTY user switches to Termax on day one
1. Install the signed per-user MSIX/MSI without admin rights.
2. First run picks the language (VI/EN) and theme; telemetry stays off by default.
3. The app detects PuTTY saved sessions and host keys and shows a preview with conflicts.
4. Commit the import; hosts are grouped, host keys go to Known Hosts, ProxyPassword moves into the vault.
5. Press Mod+K, type the host name, press Enter; the new tab opens in ≤20 ms + network RTT.

### J-00-02 An SRE handles an incident with the AI assistant and an external agent
1. Filter hosts with `tag:prod AND os:linux`, open 3 panes, enable broadcast with a confirmation because the hosts are prod.
2. Select the error log, press Mod+J to ask the AI (BYOK); it explains and proposes commands with a risk level.
3. Claude Code (MCP client) reads scrollback through the Termax MCP server in observe-only mode.
4. The agent asks to run `systemctl restart`; Termax holds the request and shows an approval card in Termax's own UI.
5. The SRE approves once for that host/session; the hash-chained audit log records it.

### J-00-03 Upgrade to Pro and sync to a second device (P2)
1. From Team & Sync, create an account with OPAQUE; the app generates a Secret Key and a recovery kit.
2. Pay through the merchant of record; the signed entitlement verifies offline.
3. The vault is encrypted client-side and pushed to oxsync; the server cannot read the contents.
4. On a second laptop or mobile, sign in with password + Secret Key and the vault decrypts locally.

## Interfaces

- **IF-00-01 Local control endpoint (termax-core)** (UDS 0600 / named pipe with user-SID DACL, per-client token): The only channel for the `tmx` CLI and the `tmx mcp` shim to talk to the running app or a headless runtime; never opens a network port.
- **IF-00-02 Termax MCP server (termax-mcp)** (MCP 2025-11-25 + 2026-07-28 over stdio shim and loopback Streamable HTTP): Exposes hosts, sessions, scrollback, SFTP and forwarding to external agents (P7), observe-only by default; detailed in BRD-08.
- **IF-00-03 LLM providers (BYOK)** (HTTPS APIs (Anthropic, OpenAI) / local Ollama): The AI assistant calls providers directly with the user's key from the OS keychain; nothing passes through Termax servers.
- **IF-00-04 oxsync API + WebSocket relay (closed)** (HTTPS + WSS): OPAQUE accounts, encrypted record sync, team vaults, multiplayer relay (P2); detailed in BRD-10/BRD-11.
- **IF-00-05 Update manifest & release CDN** (Signed manifest over HTTPS (GitHub Releases)): Signed update check, stable/beta/nightly channels, staged rollout; disclosed as the only network request before opt-in.
- **IF-00-06 OS keychain & biometrics** (Keychain/Touch ID, DPAPI + Windows Hello, libsecret): Caches the vault key and BYOK tokens; biometric unlock; detailed in BRD-06.

## Out of scope

- Porting PuTTY protocol/crypto code; SSH server functionality (psusan/uppity equivalents).
- Rlogin, SUPDUP, SSH-1 and algorithms below the “legacy” profile (DES, arcfour, blowfish, hmac-md5).
- RDP/VNC, a bundled X server, a browser-based web client.
- Termax-hosted LLM inference during the MVP (BYOK or local Ollama only).
- Windows 7/8, macOS <13, 32-bit builds, Linux without Wayland/X11 (headless use via CLI only).
- Linking any GPL component into the app; mosh is only invoked as an external process.
