# OpenSpec in Termax — guide for agents and contributors

`openspec/` is the contract between Termax's business owners and the agents and engineers who implement it. Specs say **what** the system must do; code, tests and `.principles/` say **how**.

OpenSpec CLI is pinned to **1.17.0**. Run it as `bunx @fission-ai/openspec@1.17.0 …` (or `npx`), or use the `just spec-*` recipes. Workflow skills and slash commands generated by `openspec init` live in `.claude/skills/openspec-*` and `.claude/commands/opsx/`; read them before running a workflow — they encode the method.

## Layout

| Path | Contents |
|---|---|
| `config.yaml` | Project context (product, stack, conventions, open decisions) and per-artifact rules. OpenSpec feeds it to every workflow. |
| `specs/<capability>/spec.md` | Current requirements. One capability per BRD: `product-foundation` (BRD-00) … `platform-engineering` (BRD-13). |
| `changes/<change>/` | Proposed work: `proposal.md`, `design.md`, `tasks.md`, and spec deltas under `specs/`. |
| `changes/archive/` | Applied changes, kept for history. |
| `glossary.md` | Bilingual (EN/VI) terms from the BRDs. |

The specs were generated once from the BRD YAML in the design set (`Termax_Plan.zip`, folder `02-BRD/yaml`) by `tools/openspec_from_brd.py`. From now on they change **only through OpenSpec changes**; do not regenerate over edited specs. Regenerating is only for re-importing a new BRD version into a fresh branch, followed by a diff review.

## Workflow

1. **Explore** (`/opsx:explore`): read the relevant capability specs and `config.yaml` open decisions.
2. **Propose** (`/opsx:propose` or `openspec new change <kebab-name>`): write proposal → spec deltas → design → tasks, following `openspec instructions <artifact> --change <name>`. Proposals cite the FR-/NFR- ids they implement.
3. **Validate**: `just spec-validate` (`openspec validate --all --strict`) must pass before review. CI runs the same.
4. **Apply** (`/opsx:apply`): implement tasks in order, ticking `- [x]` only when the stated verification passed.
5. **Archive** (`/opsx:archive`): after the code is merged, archive the change; deltas are merged into `specs/`.

A change that only implements existing requirements still gets a proposal and tasks; spec deltas are needed only when behaviour is added, modified or removed.

## How specs map to code, tests and contracts

- **Requirement ids** (`FR-<MODULE>-NNN`, `NFR-<BRD>-NNN`) are the join key. Put them in test names' doc comments or test module docs, PR descriptions and commit bodies — not in code comments that explain behaviour (state the invariant instead).
- **Scenarios → tests**: each `<id> acceptance N` scenario should map to an automated test or a perf metric in `cargo xtask perf`; the change's `tasks.md` names which.
- **Interfaces** (`## Interfaces`, `IF-xx-nn`) are the contract for crate APIs, the local control endpoint and MCP tools. Changing one requires a MODIFIED delta.
- **Data entities** describe stored records; schema changes in `termax-vault` need a matching delta and a migration.
- **NFR targets** are enforced by `cargo xtask perf` (targets) and its CI regression gate.
- **Modules** (`UI-xx`, `CO-xx`, `AG-xx`, …) map to crates as listed in `config.yaml` and the design set's `modules.yaml`.

## Confirmation markers

- `[TO CONFIRM · CHỜ XÁC NHẬN]` marks an undecided business question, with an owner. **Never resolve one by guessing.** Ask the owner, then record the decision in a change that removes the marker and cites who decided and when.
- Words the sources use for unverified facts ("unverified", "chưa xác minh") stay verbatim.
- "cần xác nhận" inside a requirement means the product asks the *user* to confirm an action; it is behaviour, not an open question.

## Writing rules (enforced by `--strict`)

- Every requirement contains SHALL or MUST and has at least one scenario with a GIVEN or WHEN step and a THEN step.
- Requirement bodies stay under 500 characters; put detail in scenarios.
- Keep the BRD id prefix on requirement names; new requirements take the next free number in their module.
- Specs describe observable behaviour; crate, type and function names belong in `design.md`.
